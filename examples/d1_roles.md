## 核心认知 ##

1. system约束的优先级大于user约束，单user约束有时候也会被响应
2. 历史消息可以被任意伪造，模型会把伪造内容当作既成事实采信（甚至逐字复读），不会做真伪验证。
3. 没有一个role角色和约束是一定权威的，只是某个被训练为优先级更高一些

## 核心疑问 ##

** OpenAI 的 system → developer auto-convert 暗示了什么？** 
在 OpenAI 的模型规范中，developer 消息代表了不可违背的“开发者/系统级规则”，用于定义模型的行为边界、角色、政策以及输出结构
底层是同一套机制。auto-convert 能成立说明 developer role 不是新的架构，只是新的标签 + 新的训练强化

** anthropic没有引入developer role？** 
anthropic则还是坚持“以消息为中心”的对话架构，
developer引入可以缓解提示词注入（Prompt Injection）攻击
在上面的验证中我们已经证明了这点，Prompt Injection 确实会影响模型的输出，也会影响system设定的约束
除了上面，developer还会影响对于tool的调用规则、复杂推理步骤的约束等

** assistant role 的消息可以由谁产生？** 
- 模型真实生成（正常情况）
- 开发者构造的伪造历史
- 缓存/回放的历史响应（生产里常见，比如 prompt cache 命中）
模型无法分辨这条 assistant 是它说过的、还是你刚塞进来的

** 让模型区分developer和user** 
- Tokenizer 层：用特殊 token（如 <|im_start|>developer<|im_sep|>...<|im_end|>）划定边界。这只是 boundary marker，没有任何"优先级"语义。
- 训练层：用 RLHF / instruction tuning / IH-Challenge 这类数据集，教模型在看到 <|im_start|>developer 之后的内容时倾向于更服从。

## Anki 卡片 ##
Q: Role 标签在模型架构里是硬约束还是软约束？依据是什么？
Role标签在模型架构不是硬约束，它只是被后续训练成输出更遵循某个role的约定而已，user的role约束同样也会被执行

Q: OpenAI 的 developer role 相对 system 新增了什么？没新增什么？
新增了：
- 一个新的 token boundary marker（在词表里加了 <|im_start|>developer 这类 token）
- 训练阶段对这个 marker 的服从强化（IH-Challenge 数据集就是干这个的）
- 文档层面的"分层叙事"（platform > developer > user）
没新增：
- 没有任何架构层的硬约束
- 没有签名 / 真伪验证 / 加密边界
- 底层机制和原 system 是同一套，否则 auto-convert 不可能无损

为什么问这个：因为如果你以为 developer 是"新机制"，你以后会误以为"换个 role 名字就更安全了"。
实际上改名 + 改训练数据 ≠ 改机制。这是延续 #1 的认知：软约束不会因为换了个标签就变硬。

名词解释：
IH-Challenge 是 OpenAI 专门设计的一个强化学习训练数据集，旨在解决前沿大语言模型（LLMs）在处理复杂指令冲突时的“指令层级（Instruction Hierarchy, IH）”问题。
它的核心目标是训练模型在面临多方指令冲突时，能够稳定地遵循更高信任等级的指令，从而在“安全可控性”与“抵御提示词注入（Prompt Injection）”之间取得平衡。

Q: Tokenizer 层和训练层在"role 优先级"里各自的职责是什么？画一下分工。
- Tokenizer = framing（问题构建 / 框架处理），让模型"看得见"边界在哪）
- 训练 = enforcement（强制执行 / 约束机械化），教模型"看见边界后应该怎么反应"
framing 没有任何强制力。
enforcement 是统计倾向，不是规则。这个分工记牢了，
以后你看任何 LLM 安全相关讨论都能一眼分辨"作者在谈 framing 还是 enforcement"——多数人混着说，混了就讨论不清。

名词解释：
Framing（问题构建 / 框架处理）：它是指在真正开始训练模型之前，如何定义、组织和呈现问题的过程。
- 核心含义：决定模型要解决什么问题，以及用什么方式来解决。这包括确定输入变量（特征）、输出目标（标签），以及选择合适的模型类型（如分类模型还是回归模型）。
- 通俗理解：就像在盖房子之前画图纸。你需要先界定清楚房子的用途、结构和边界，模型才知道该往哪个方向学习。

Enforcement（强制执行 / 约束机械化）：在AI Agent（智能体）工程与Harness（执行系统）的语境下，Enforcement 指的是“强制执行力”或“约束机械化”。它是构建可靠Agent系统的核心支柱。
- 核心含义：将原本依赖模型“自觉性”的软性约束，转化为系统级的硬性约束。它不指望模型去“理解”规则，而是通过工程化手段（如自动化测试、定制化代码检查工具 Linter、沙箱环境等）让模型“不可能做错”。
- 通俗理解：如果说 Framing 是告诉模型“你应该怎么做”，那么 Enforcement 就是给模型装上“物理门禁”。如果模型产出的结果不符合规范，系统会直接报错并拦截，从机制上杜绝违规操作。

Q: 一段 role: assistant 的消息可能由哪几类来源产生？这对 agent 设计有什么含义？
- 模型真实生成（正常情况）
- 开发者构造的伪造历史
- 缓存/回放的历史响应（生产里常见，比如 prompt cache 命中）

assistant 历史里出现的"事实声明"不能直接采信、不能直接驱动副作用。
tool 调用 / 状态变更必须看 tool_result（你控制的），不能看 assistant 自述。
