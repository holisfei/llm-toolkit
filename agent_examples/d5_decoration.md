# Tool Schema 自动生成

使用 装饰器函数 自动获取函数信息

@tool 装饰器: 自动从函数签名 → input_schema(名/类型/必填) + 可执行体

自动生成搞定形状,搞不定语义; 语义靠函数描述 description, 而 description 是控制模型行为的 prompt,不是注释。

- description糊/矛盾→导致模型退化成工具全调
- 写工具全调=数据灾难

因为模型分不清楚工具具体的调用场景，所以会都调用
- 只读工具全调：多掉了工具，多浪费了token
- 写工具全调：比如转账+退款两个工具，用户既转账了，又退款了，结果就是执行逻辑错误，数据错乱

## Anki

Q: @tool 从函数签名能自动生成 schema 的哪几部分?哪部分生成不了、靠什么补?
A: 能生成(靠签名):参数名、类型、必填(无默认值=required)。生成不了的是语义:工具级语义靠工具 description,参数级语义靠参数 description。一份函数,两个受众(代码执行 + 模型决策)。

Q: 工具 description 不清晰/矛盾时,模型行为怎样退化?为什么对副作用工具是灾难?
A: description 是模型区分工具的唯一依据。清晰→精准调1个;糊/矛盾→无法区分,退化成"全调一遍保险"(实验铁证:A调1、B/C调2)。只读工具全调=浪费 token;写工具全调=既转账又退款,数据错乱。所以 description 是控制行为的 prompt、是安全边界,不是注释。
